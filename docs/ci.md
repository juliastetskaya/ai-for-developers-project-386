# CI pipeline

Every push and pull request runs one shared workflow: `.github/workflows/check.yml`
(workflow name `check`). Feature tickets do not add their own CI — they extend this
pipeline. `.github/workflows/hexlet-check.yml` is generated by Hexlet and must not be
edited. Releases are automated separately on push to `main` by
`.github/workflows/release-please.yml` (see [releases.md](releases.md)); it is not part of
the PR check pipeline.

## What the pipeline does

The workflow has two independent jobs.

### `check` (push and pull request)

1. `actions/checkout` — checks out the PR head; no repository secrets are used.
2. `jdx/mise-action` — installs the pinned toolchain from `mise.toml`
   (Node, pnpm, hk, pitchfork, actionlint).
3. `mise run setup` — `pnpm install` + `pnpm generate:api` (TypeSpec → OpenAPI → SDK).
4. `pnpm exec playwright install --with-deps chromium` — the browser for the golden path.
5. `mise run check` — the same gate developers run locally.

### `docker` (pull request only)

The second job installs the same mise toolchain and runs `mise run docker:build`
(`docker build --tag cal-clone:local .`). It guards the production artifact — `Dockerfile`,
`.dockerignore`, `docker-entrypoint.sh` and the same-origin SPA build — which the `check`
gate never touches. It runs on pull requests only and is not part of `mise run check`:
the image build takes several minutes and would slow down the main gate.

`mise run check` fans out to:

| Task        | What it proves                                                        |
| ----------- | --------------------------------------------------------------------- |
| `lint`      | oxlint (type-aware for the backend) passes for every package, plus `e2e/`, `playwright.config.ts` and `scripts/`. |
| `typecheck` | `tsc` passes for backend, frontend (`tsc -b`), the API client, and the golden-path files (`tsconfig.e2e.json`). |
| `test`      | backend unit tests, backend e2e tests, then frontend component tests. |
| `e2e:golden` | the Playwright guest flow against real backend + frontend servers and a dedicated SQLite database; the booking API is never mocked. |
| `build`     | backend (`nest build`) and frontend (`vite build`) compile.           |
| `check:sdk` | regenerating the SDK produces no diff (generated artifacts are fresh).|
| `check:versions` | every workspace package uses the root `package.json` version.       |
| `check:release-please` | release-please config: one root package, manifest version matches the root, every workspace manifest is in `extra-files`. |
| `check:ci`  | CI config invariants (`scripts/ci-config.test.mjs`) + `actionlint`.   |

Each task exits non-zero on failure, `mise` propagates a failed dependency, and the
workflow step fails with it. A green job therefore means every gate passed.

The workflow runs with `permissions: contents: read`, has no `secrets.*` references,
and is safe for pull requests from forks.

## Run the gates locally

```bash
mise install            # install the pinned toolchain once
mise run setup          # install dependencies and regenerate the SDK

mise run lint           # lint
mise run typecheck      # types
mise run test           # backend unit + backend e2e + frontend
mise run test:e2e       # backend e2e only (independent)
mise run e2e:golden     # Playwright golden path (also part of `check`)
mise run build          # backend build + frontend build
mise run docker:build   # production Docker image (also a separate PR job in CI)
mise run check:sdk      # generated SDK freshness
mise run check:versions # single-version drift across workspace packages
mise run check:release-please # release-please config matches the single version
mise run check:ci       # workflow/config validation
mise run check          # everything above, exactly what CI runs
```

Individual package commands remain available: `pnpm --filter backend test:e2e`,
`pnpm --filter backend build`, `pnpm --filter frontend build`, etc.

The Playwright golden path (`mise run e2e:golden`) is part of `mise run check`, so it runs
both locally and in CI with the real backend and frontend and a dedicated SQLite database.
It uses dedicated ports `3100` (API) and `5273` (frontend), so it does not collide with the
dev servers on `3000`/`5173`. Its TypeScript and scripts are also covered offline: `lint`
runs oxlint over `e2e/`, `playwright.config.ts` and `scripts/`, and `typecheck` runs
`tsc -p tsconfig.e2e.json`. It is documented in
[architecture.md](architecture.md#тестирование).

## Required status check / branch protection

The required check is applied on `main` (the repository's default branch). Configured
with the GitHub CLI:

```bash
gh api --method PUT repos/{owner}/{repo}/branches/main/protection --input - <<'JSON'
{
  "required_status_checks": {
    "strict": true,
    "contexts": ["check"]
  },
  "enforce_admins": true,
  "required_pull_request_reviews": null,
  "restrictions": null,
  "allow_force_pushes": false,
  "allow_deletions": false,
  "required_conversation_resolution": true
}
JSON
```

Verify it:

```bash
gh api repos/{owner}/{repo}/branches/main/protection \
  --jq '{checks: .required_status_checks.contexts, strict: .required_status_checks.strict, enforce_admins: .enforce_admins.enabled}'
```

`check` is the workflow/job name from `check.yml`; if the job is renamed, update the
required context too. The protection requires admin permission on the repository — if
the API answers `403`, the repository owner must run the command above.

The `docker` job is deliberately **not** a required status check: it only guards the
production artifact, and a red image build must not block merging unrelated fixes. Treat it
as a signal — if GitHub reports a failing `docker` check on a PR, fix or explicitly discuss
it before merging.

`integration/call-calendar` is currently a local integration branch and is not pushed
to `origin`. If it becomes a remote branch that receives PRs, protect it with the same
payload and `branches/integration%2Fcall-calendar/protection` in the URL.
