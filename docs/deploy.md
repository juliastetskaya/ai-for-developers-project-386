# Деплой на Render

Прод — тот же единственный Docker-образ, что собирается локально: NestJS backend
раздаёт собранный React SPA и API на одном порту. Docker-часть описана в
[README](../README.md#docker), инфраструктура Render — в [`render.yaml`](../render.yaml).

Деплой рассчитан на **бесплатный план** Render: сервис живёт на `*.onrender.com`, диск не
используется, SQLite хранится на эфемерной файловой системе контейнера.

## Что описано в `render.yaml`

| Поле | Значение и причина |
| --- | --- |
| `runtime: docker` | сборка из `./Dockerfile` (multi-stage: install → generate SDK → build → prod deps). |
| `plan: free` | бесплатный инстанс: без диска, с засыпанием после простоя. |
| `branch: main` | деплоятся только коммиты из `main`. |
| `region: frankfurt` | ближайший регион к владельцу календаря (`Europe/Moscow`). |
| `healthCheckPath: /health` | Render считает деплой успешным только при `{"status":"ok"}`. |
| `autoDeployTrigger: checksPass` | деплой запускается после зелёного workflow `check` на коммите. |
| `DATABASE_URL=file:/data/app.db` | путь к SQLite внутри контейнера (на free-плане — эфемерный). |
| `PORT=10000` | порт, который Render пробрасывает в контейнер и по которому маршрутизирует трафик. |

Блок `disk` в `render.yaml` закомментирован: диски доступны только на платных планах.

## Контракт порта

Render передаёт порт через переменную окружения `PORT` (по умолчанию `10000`) и ждёт,
что HTTP-сервер слушает `0.0.0.0:$PORT`.

- `apps/backend/src/main.ts` читает `process.env.PORT` и падает обратно на `3000`, только
  если переменная не задана. Хардкода порта в образе нет — в `Dockerfile` остался лишь
  `EXPOSE 3000` как документация локального значения по умолчанию.
- Nest слушает все интерфейсы, поэтому биндинг на `0.0.0.0` выполняется без дополнительных
  флагов.
- Docker `HEALTHCHECK` и Render health check используют один и тот же `PORT`, поэтому при
  смене порта в Dashboard ничего править не нужно: поменяйте `PORT` в `render.yaml`
  (или в Dashboard) — приложение, healthcheck и маршрутизация останутся согласованными.
- Локально то же поведение проверяется командой:

  ```bash
  docker build -t cal-clone:local .
  docker run --rm -e PORT=10000 -p 10000:10000 cal-clone:local
  curl -fsS http://localhost:10000/health
  ```

## Первый деплой

1. В Render Dashboard: **New → Blueprint**, подключить GitHub-репозиторий — Render найдёт
   `render.yaml` в корне.
2. Подтвердить создание сервиса `cal-clone`. Первый билд собирает образ (несколько минут)
   и поднимает сервис на `https://cal-clone.onrender.com`.
3. Проверить `https://cal-clone.onrender.com/health` и открыть корень — SPA и API должны
   работать с одного origin.
4. Запросы к API можно слать через MCP-сервер Render (`opencode.json`): он умеет смотреть
   логи, метрики и деплои, менять переменные окружения и запускать редеплой. Render не
   поддерживает OAuth dynamic client registration, поэтому сервер настроен на авторизацию
   по API-ключу: `oauth: false` и заголовок `Authorization: Bearer {env:RENDER_API_KEY}`.
   Ключ создаётся в [Account Settings → API Keys](https://dashboard.render.com/u/settings?add-api-key)
   и передаётся через переменную окружения `RENDER_API_KEY` процесса OpenCode.

## Данные и миграции

- На free-плане SQLite лежит в `/data/app.db` внутри контейнера. Каталог создаётся в
  образе, но **не переживает** деплой, рестарт и засыпание сервиса: после каждого
  пробуждения база пустая, а миграции применяются заново. Для демо это нормально, для
  сохранения броней — нет.
- Миграции Prisma (`apps/backend/prisma/migrations`) применяются при старте контейнера в
  `DatabaseService`; отдельный `preDeployCommand` не нужен. Повторный запуск безопасен:
  применённые миграции записаны в таблицу `_migrations`.
- Контейнер работает от пользователя `node`: entrypoint стартует от `root` лишь для того,
  чтобы выставить владельца `/data` (диск Render приезжает root-owned), и сразу сбрасывает
  права через `setpriv`. Если платформа запускает контейнер не от root, chown пропускается.

## Как включить постоянное хранение

Диски Render доступны только на платных инстансах. Чтобы данные переживали деплой:

1. В `render.yaml` замените `plan: free` на платный план, например `plan: 0.5c-512mb`.
2. Раскомментируйте блок `disk` (`mountPath: /data`, `sizeGB: 1`).
3. `DATABASE_URL` уже указывает на `file:/data/app.db` — он должен оставаться внутри точки
   монтирования, иначе база снова окажется на эфемерной ФС.
4. Задеплойте: первый деплой с диском создаст его и включит ежедневные снапшоты (хранятся
   7 дней).

## Ограничения бесплатного плана

- **Нет диска:** данные SQLite обнуляются при деплое, рестарте и после простоя.
- **Засыпание:** после ~15 минут без трафика сервис останавливается; первый запрос после
  паузы ждёт холодного старта (до минуты и больше).
- **Один инстанс и без zero-downtime:** на время деплоя сервис недоступен.
- Лимит бесплатных часов в месяц исчерпывается при активном использовании.

## Связь с CI

Деплой не входит в `mise run check` и не требует секретов в CI: сборка образа и Blueprint
проверяются Render на своей стороне. `autoDeployTrigger: checksPass` лишь не даёт выкатить
коммит с красным `check`.

Сам образ отдельно собирается в CI задачей `docker` на pull request (`mise run docker:build`):
поломка `Dockerfile`, `.dockerignore` или entrypoint видна до мёржа. Эта задача не является
обязательным статусом — её красный результат нужно разобрать, но он не блокирует merge.
