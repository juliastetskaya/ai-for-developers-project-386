# AGENTS.md

## Overview

Cal.com-like booking calendar (Hexlet student project). pnpm monorepo, Russian-language docs/spec.

- `apps/backend` — NestJS 12 (ESM), Vitest, oxlint
- `apps/frontend` — React 19 + Vite + Tailwind CSS 4 + shadcn, Vitest + Testing Library
- `typespec` — TypeSpec API spec, compiles to `tsp-output/.../openapi.yaml`
- `packages/api-client` — typed SDK generated by `@hey-api/openapi-ts` into `src/client/`

Generated paths — never hand-edit; both are regenerated by `pnpm generate:api` and are gitignored:

- `typespec/tsp-output/` — generated OpenAPI from `typespec/main.tsp`
- `packages/api-client/src/client/` — generated TypeScript SDK from that OpenAPI

No suitable NestJS server-code generator is configured, so backend controllers are hand-written
and kept in sync with the contract by the API e2e tests.

## Toolchain

All tools (Node 22, pnpm 10, hk, pitchfork) are pinned in `mise.toml`. Install via `mise install`, then `mise run setup` (installs deps + generates SDK). Run tasks through `mise run <task>` rather than calling pnpm scripts directly when a task exists.

## Key commands

- `mise run dev:backend` / `mise run dev:frontend` — dev servers (ports 3000 / 5173)
- `mise daemons start` — both dev servers as background daemons (pitchfork); also `ls` / `logs` / `stop`
- `mise run check` — the full gate: lint + typecheck + tests (unit + e2e) + the real-server browser golden path + build + SDK freshness + single-version drift + CI config validation. **This is what CI runs; make it pass before finishing any change.**
- `mise run build` / `mise run test:e2e` / `mise run e2e:golden` — build both apps / run backend e2e tests / run the Playwright golden path independently.
- `pnpm generate:api` — recompile TypeSpec and regenerate the SDK. Required after touching `typespec/`; `mise run check` fails with a diff if the generated client is stale.

## Testing

- Backend: `pnpm --filter backend test` (vitest run). Single file: `pnpm --filter backend exec vitest run <file>`. E2E: `pnpm --filter backend test:e2e` (separate config `vitest.config.e2e.ts`).
- Frontend: `pnpm --filter frontend test`; single file the same way with `exec vitest run <file>`.
- Root `pnpm test:backend` / `pnpm test:e2e` / `pnpm test:frontend` run suites sequentially; `mise run test` = backend unit + backend e2e + frontend.

## Git conventions

Git hooks are managed by [hk](https://hk.jdx.dev/) (`hk.pkl`):

- `pre-commit` — lint
- `pre-push` — full `mise run check`
- `commit-msg` — **Conventional Commits enforced**: messages must match `type(optional-scope): description`, e.g. `feat: add booking endpoint`, `fix(slots): exclude occupied intervals`. Valid types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. Non-conforming messages are rejected. The implementation commit references the ticket it closes, for example: feat: booking an available slot (#12).

Do not bypass hooks (`--no-verify`) — CI re-runs the same checks.

## CI

- `.github/workflows/check.yml` — the single shared pipeline: `mise run setup`, Playwright browser install, then `mise run check` on every push/PR. It also builds both apps, runs backend e2e and the real-server browser golden path; no repository secrets, safe for fork PRs.
- `.github/workflows/release-please.yml` — release automation on push to `main`: Release PR with a single project version and CHANGELOG, then a GitHub Release and `vX.Y.Z` tag after merge. See [`docs/releases.md`](docs/releases.md).
- `.github/workflows/hexlet-check.yml` — auto-generated by Hexlet; **do not edit or delete**.
- `main` is protected: the `check` status is required (strict, admins enforced). The pipeline, local gates and the branch-protection commands are documented in [`docs/ci.md`](docs/ci.md). If a new workflow/job name replaces `check`, update the required status context.

## Gotchas

- Linter is **oxlint**, not ESLint (backend uses `--type-aware` via `oxlint-tsgolint`).
- Frontend `typecheck` is `tsc -b` (project references), not plain `tsc --noEmit`.
- Business rules worth knowing before changing booking logic: slots are sliced from a fixed working-hours window; any time overlap with **any** booking (of any meeting type) makes a slot unavailable globally; no auth, cancellation, or per-user timezone selection by design — the owner timezone is a fixed constant (`Europe/Moscow`, see `docs/adr/0003-owner-timezone-and-booking-horizon.md` and README).
